## Problem Statement
在 2026 年 3 月 19 日这个时间点，找出“已经明显升温，但供给仍然稀缺”的项目方向，优先适合独立开发者、小团队或 side project 切入。

## What Makes This Cool
不是再做一个新的通用 AI agent，而是补齐 2026 年 agent 化、语音化、垂直化之后留下的结构性缺口：

- agent 会做事了，但还没人把“可审计、可协作、可控”做透
- 垂直行业开始上 AI，但“证据链、合规、可追溯”仍然缺产品
- 语音与环境感知开始起来，但跨平台、低摩擦、真实有用的体验仍然少

## Constraints
- 适合 1-3 人在 2-6 周内做出第一版
- 最好能先做 wedge，不依赖大规模销售或重实施
- 需要有明确的“为什么是现在”
- 尽量避开最拥挤的通用 chat / 通用 agent 壳层

## Premises
1. 2026 年 3 月最热的主线不是“聊天更聪明”，而是“agent 开始自动执行任务”。这个前提大概率成立。
2. 真正稀缺的机会不在新的基础模型，而在 agent 的信任层、协作层、垂直工作流层。这个前提大概率成立。
3. 最好的切入方式不是做大而全平台，而是做一个高频、高痛、能立即替代人工检查的窄工作流。这个前提大概率成立。

## Approaches Considered
### Approach A: Agent Flight Recorder
做一个跨 Cursor / Codex / OpenClaw / 自建 agent 的“飞行记录仪 + 审批台 + 审计日志”。

Why now:
- Cursor 在 2026-03-05 发布了可自动运行的 agents 和 automations。
- OpenAI 在 2026-03-06 发布 Codex Security，说明 agent 产出的安全审查已经成瓶颈。
- Product Hunt 在 2026-03-03 和 2026-03-06 上，出现了 Continue Mission Control、AgentCenter for OpenClaw、Vet、CoChat 等“agent 管理/质控”产品，说明需求很热。

What to build first:
- 接 GitHub + Slack
- 记录 agent 做了什么、用过哪些工具、改了哪些文件、准备发什么消息
- 做一个高风险动作审批
- 给团队一个可回放时间线

Pros:
- 热度最强
- B2B 愿意付费
- 适合从窄 wedge 起步

Cons:
- 需要较强产品定义，不能只做日志界面
- 很容易做成“看起来重要但没人天天开”的 dashboard

### Approach B: Evidence Layer for Regulated Work
做一个“证据链工作台”，先选一个强监管、高认知负荷场景，比如医疗、科研、法律、咨询中的单一流程。

Why now:
- OpenAI 在 2026-01-08 发布 OpenAI for Healthcare，把“透明引用、审计日志、HIPAA 支持”直接产品化。
- OpenAI 在 2026-01-27 发布 Prism，把科研写作与协作工作流 AI 原生化。
- Anthropic 在 2026-02-17 和 Infosys 的合作也直接强调了 regulated industries 需要 governance and transparency。

What to build first:
- 只做一个工作流
- 例如“医学文献快速综述 + 引用核查 + 输出摘要”
- 或“科研 paper 的 claim-to-citation 检查”
- 每条结论都能回溯到来源

Pros:
- 更难被通用 agent 直接替代
- 用户愿意为“少犯错”买单
- 一旦切中场景，粘性很强

Cons:
- 必须有明确行业理解
- 不能泛泛做成“AI 搜索 + 引用”

### Approach C: Listener-Side Communication Layer
做一个面向全球团队的“听者侧沟通增强层”，重点不是转写，而是实时理解。

Why now:
- Krisp Accent Conversion 在 2026-03-03 登上 Product Hunt 高位。
- Krisp 也在 2026-03-03 正式发布 listener-side Accent Conversion，说明市场开始从“说话的人”转向“听的人怎么更容易理解”。
- Product Hunt 同期还出现了 GHOSTYPE、SuperPowers AI 这类语音/环境交互产品，说明交互形态在升温。

What to build first:
- Zoom / Meet / Teams 的桌面层插件
- 实时识别专业术语、口音理解风险、歧义句
- 会后输出“哪些地方可能被听错了”

Pros:
- 体验有 wow factor
- 用户一试就知道值不值
- 有机会做出真正差异化

Cons:
- 音频链路和跨平台集成较难
- 产品体验要求高，差一点就没人留

## Recommended Approach
优先做 Approach A。

理由：
- 这是 2026 年 3 月最明确的一条主线，需求已经被多家工具和平台验证。
- 但现有产品大多是单平台、单点工具，还没有形成一个真正跨 agent 的“信任操作系统”。
- 对独立开发者来说，最容易先拿下一个高价值 wedge，例如“GitHub PR agent 审批与回放”。

## Open Questions
- 你更想做 B2B 工具，还是偏个人生产力 / 消费者体验？
- 你是否有现成 domain advantage，比如医疗、科研、外包、跨境客服、开发工具？
- 你更擅长前端产品、系统集成，还是语音 / 模型相关工程？

## Success Criteria
- 7 天内能做出首个可演示原型
- 14 天内能让 3-5 个真实用户试用
- 用户会说出明确反馈，不是“挺有意思”，而是“这个我每天都能用”
- 能量化省下来的时间、减少的错误，或降低的风险

## Next Steps
1. 先选一个方向，不要同时做三个。
2. 如果选 Approach A，第一版只做 GitHub PR + Slack 审批。
3. 如果选 Approach B，先锁死一个行业和一个输出格式。
4. 如果选 Approach C，先做“会后歧义检测”而不是完整实时音频重写。
5. 用一个周末做出可演示版本，再拿给 5 个目标用户看。

## What I noticed about how you think
- 你问的不是“现在什么最火”，而是“什么比较火但是却比较稀缺”，说明你在找供需错位，而不是追热点。
- 你把时间点钉在“2026 年 3 月 19 日”，说明你要的是窗口判断，不是长期空谈。
