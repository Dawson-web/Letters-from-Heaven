## Review Goal
对 `云端回信` 小程序的前端技术方案做一次工程审查，输出一份适合团队讨论和技术分享的栈建议。

- v1 该选什么

## Step 0: Scope Challenge

### 这是什么类型的前端产品
`云端回信` 不是高互动社交产品，也不是高并发电商前台。它更像：
- 高敏感文本产品
- 低频但高情绪价值
- 页面不多，但每个页面都要稳
- 对“边界感、信任感、静谧感”要求很高

这决定了前端技术方向：
- `稳定性` 比 `炫技` 重要
- `克制的复杂度` 比 `跨端幻想` 重要
- `小程序原生体验` 比 `一套代码跑 everywhere` 更重要

### What already exists
- 现有代码：无
- 现有设计结论：已有 office-hours 设计稿，推荐的是“思念回响/云端回信”这条非拟人化、延迟回信路线
- 现有约束：只讨论小程序前端，不扩展到 H5/App/后台实现

### Minimum set of changes
如果只做 v1，前端最小闭环应当只有这些：
- 首页 / 品牌说明
- 写信页
- 发送成功页
- 回信收件箱
- 回信详情页
- 个人与设置页
- 安全边界与免责声明

不需要：
- 实时聊天
- 复杂社交关系链
- 多端统一框架
- 大型状态管理系统

### Complexity check
如果 v1 一开始就选：
- `Taro/uni-app 多端`
- `大型 UI 库`
- `全局状态库 + 数据缓存库 + 事件总线`
- `Skyline + 高级动效体系`

那就是过度设计。

这个产品的前端 complexity budget 很有限。工程上应坚持：
- 一个主运行时
- 一种页面组织方式
- 一个轻量数据流
- 一个可测试的请求层

### Completeness check
完整方案不等于上更多框架，而是把该做的基础能力一次做好：
- TypeScript 类型
- 请求层与错误态
- 草稿保存
- 空态 / 异常态 / 慢网态
- 测试骨架
- 日志与发布流程

### Step 0 Recommendation
推荐：

`微信原生小程序 + TypeScript + 原生自定义组件 + 轻量服务层`

不推荐 v1 上来就做跨端。

原因：
- 这是一个单端验证产品，先做对，不先做广
- 小程序体验、审核、边界提示、订阅消息、存储、分享链路都更贴近原生能力
- 前端团队不需要为了一个 6 页产品，先支付跨端抽象税

## 1. Architecture Review

### 技术栈候选对比

#### Approach A: 微信原生小程序
- Summary: 使用微信开发者工具和原生小程序结构，配 TypeScript、自定义组件、原生 API。
- Effort: S
- Risk: Low
- Pros:
  - 最贴近微信能力和审核语境
  - 包体、性能、兼容、调试最可控
  - 适合低页面数、强体验控制的产品
- Cons:
  - 多端复用弱
  - 团队若全是 React/Vue 背景，上手会有一点摩擦

#### Approach B: Taro 4 + React + TypeScript
- Summary: 用 React 心智开发小程序，后续可以拓展 H5/其他端。
- Effort: M
- Risk: Med
- Pros:
  - React 团队上手快
  - 后续跨端扩展空间更大
  - 文档和生态成熟
- Cons:
  - 运行时与构建链更重
  - 小程序边界问题排查会更绕
  - 为一个纯微信 v1 提前支付了跨端成本

#### Approach C: uni-app + Vue 3 + TypeScript
- Summary: 用 Vue 体系开发，多端能力强，国内团队熟悉度也高。
- Effort: M
- Risk: Med
- Pros:
  - 多端很强
  - Vue 团队接受度高
  - 周边生态丰富
- Cons:
  - 同样在为未来跨端预付复杂度
  - 页面细节和小程序原生调试路径不如原生直接
  - 对这个题材，抽象层越厚，越不利于打磨气质

### Recommendation
选择 `Approach A: 微信原生小程序`。

这是典型的 `Choose Boring Technology` 场景。你只有 3 个创新 token，不该浪费在框架层。这个产品真正该创新的是：
- 回信体验
- 文案边界
- 仪式感
- 安全感

不是前端跨端架构。

### 推荐前端栈

#### 运行时与语言
- `微信原生小程序`
- `TypeScript`
- `wechat-miniprogram/api-typings` 作为 API 类型基础

理由：
- 原生能力最直接
- TS 能把请求层、页面参数、组件 props 和状态边界守住

#### 组件与页面层
- `原生自定义组件`
- `SCSS`
- 少量共享基础组件，自建，不引入整套电商风 UI 库

建议只做这些基础组件：
- `SafePage`
- `LetterCard`
- `ReplyCard`
- `EmptyState`
- `LoadingState`
- `PrimaryButton`
- `SoftDialog`

不建议整库引入 Vant 一类组件库。原因不是它不好，而是气质不对，会把产品做得太像常规工具/商城。

#### 状态管理
推荐：
- 页面内状态：页面 `data`
- 跨页轻状态：单个 `appStore/sessionStore`
- 草稿状态：`storage` 封装

不推荐 v1 上 Redux / MobX / Zustand 风格的大状态管理。

这是一个页面数量少、共享状态少的产品。硬上全局状态库，只会制造同步问题。

#### 数据请求
推荐：
- 一层 `request` 封装
- 一层 `services`
- 一层 `adapters/guards`

目录建议：

```text
miniprogram/
  services/
    request.ts
    auth.ts
    letters.ts
    replies.ts
    profile.ts
  adapters/
    letter.ts
    reply.ts
  utils/
    storage.ts
    logger.ts
    time.ts
```

核心原则：
- 页面不直接调 `wx.request`
- 页面只拿干净 DTO
- AI 回信数据必须经过显式判空和字段校验

#### 异步回信机制
前端不要做成“聊天连接”。

推荐：
- 写信后创建 `replyJob`
- 成功页展示“预计回信时间”
- `onShow` 刷新 + 手动下拉刷新
- 可选：订阅消息提醒

不推荐：
- WebSocket
- SSE
- 长连接轮询动画

这是一个“慢回复”产品，不是 IM。

#### 日志与可观测性
前端至少要有：
- `logger.ts` 封装
- 页面级 trace id
- 关键动作埋点：开始写信、保存草稿、发送成功、打开回信、删除草稿
- 敏感内容不上报全文

生产日志建议对接：
- 小程序实时日志能力

#### 发布链路
推荐：
- 本地开发：微信开发者工具
- Lint/Test：Node 脚本
- 构建发布：`miniprogram-ci`

### 一个现实生产故障场景
故障：
用户写完信点击发送，接口成功写入了信件，但前端因为弱网超时，以为发送失败。

如果前端没做幂等和状态回查，用户会重复发送多封。

方案必须包含：
- 前端发送按钮防重入
- client request id
- 发送失败后主动查一次最近信件状态

## 2. Code Quality Review

### 目录组织建议

```text
miniprogram/
  app.ts
  app.json
  app.scss

  pages/
    home/
    write/
    sent/
    inbox/
    reply-detail/
    profile/
    settings/

  components/
    safe-page/
    letter-card/
    reply-card/
    empty-state/
    loading-state/
    primary-button/
    soft-dialog/

  services/
  adapters/
  utils/
  constants/
  types/
```

### Code quality recommendations
1. `页面只管交互，不管协议`
页面负责展示和动作，不负责拼接口字段。

2. `所有 AI 相关返回都要过 adapter`
因为这个产品最危险的不是 500，而是“返回了看起来像对的、其实不该直接展示的内容”。

3. `不要把文案硬编码在多个页面`
边界提示、免责声明、发送说明、空态说明，都要集中管理。

4. `不要过早抽象成 hooks 风格工厂`
这是原生小程序，不是 React 应用。能显式就显式。

5. `日志和埋点要物理分开`
运维日志记录错误上下文，埋点只记录业务行为，避免后续泄露敏感信件内容。

### 应避免的反模式
- 页面直接 request
- 页面直接处理 response schema
- 组件读写 storage
- 组件里塞业务逻辑
- UI 库样式覆盖到处写
- 把“回信生成中”做成假实时打字动画

## 3. Test Review

### Test diagram

```text
ROUTES / FEATURES

1. 首页
   - 首次进入
   - 免责声明确认
   - 进入写信

2. 写信页
   - 输入标题/正文
   - 选择关系标签
   - 草稿自动保存
   - 离开再回来恢复
   - 空内容禁止发送
   - 重复点击发送防抖

3. 发送成功页
   - 展示等待状态
   - 展示预计回信时间
   - 返回收件箱

4. 收件箱
   - 无回信空态
   - 有回信列表
   - waiting / ready 状态显示
   - 下拉刷新

5. 回信详情页
   - 正文展示
   - 异常文案兜底
   - 分享/收藏/导出入口是否展示

6. 设置页
   - 边界声明
   - 隐私说明
   - 删除草稿/退出
```

### 推荐测试层次

#### 单元 / 组件测试
- `miniprogram-simulate`
- `jest`

测什么：
- 组件空态、禁用态、错误态
- 发送按钮 loading / disabled
- 回信卡片状态显示

#### 集成 / 页面测试
测什么：
- 草稿恢复
- 重复发送拦截
- 接口异常后的 UI 反馈
- 从 waiting 到 ready 的刷新路径

#### 端到端测试
- `miniprogram-automator`

测什么：
- 首次打开 -> 同意说明 -> 写信 -> 发送 -> 收件箱查看状态
- 弱网 / 接口失败 / 返回空数据时用户是否能看懂

### 必须覆盖的失败模式

| Codepath | 失败方式 | 测试覆盖 | 错误处理 | 用户感知 |
|---|---|---|---|---|
| send letter | 接口超时但服务端已入库 | 必须 | 必须 | 清晰提示，不重复发送 |
| load inbox | 返回空数组 | 必须 | 必须 | 正常空态 |
| load reply detail | reply id 无效 | 必须 | 必须 | 失效提示 |
| restore draft | storage 数据损坏 | 必须 | 必须 | 清空并提示 |
| boundary acceptance | 用户未确认说明 | 必须 | 必须 | 禁止进入写信 |

### Test review verdict
如果这些失败模式没有测试，这个前端方案就不算完整。

## 4. Performance Review

### 重点不是 FPS，而是稳定感
这个产品不是长列表短视频，不需要把性能优化做成秀肌肉。

真正要注意的是：

1. `setData 颗粒度`
- 不要正文每敲一个字就全页面 setData
- 编辑器状态要按字段更新

2. `草稿保存节流`
- 不要每次输入都写 storage / 调接口
- 推荐 `800ms~1500ms` debounce

3. `首屏轻`
- 首页只放必要文案和 CTA
- 不要首页塞沉重动画、背景视频、大图

4. `图片和字体克制`
- 这个题材应该靠留白、排版和动效节奏，而不是资源堆砌

5. `分包策略`
- v1 可以先不拆
- 但目录结构要为后续拆包做好准备
- 若后续加纪念册、打印、家庭空间，再把低频页拆子包

### 不建议现在做的性能项
- Skyline 首发
- 虚拟列表
- WebSocket 实时刷新
- 自研富文本编辑器

## Failure Modes
1. 发送成功但前端显示失败
- 是否有测试：应有
- 是否有错误处理：应有
- 是否会静默失败：如果不做幂等与回查，会

2. 回信为空或字段异常
- 是否有测试：应有
- 是否有错误处理：应有
- 是否会静默失败：如果页面直接展示原始数据，会

3. 草稿损坏导致页面崩溃
- 是否有测试：应有
- 是否有错误处理：应有
- 是否会静默失败：会

4. 用户误解为逝者真实回复
- 是否有测试：应做文案与入口验证
- 是否有错误处理：应有前端边界提示
- 是否会静默失败：会，这是产品级事故

### Critical gaps to avoid
- 没有发送幂等
- 没有异常态页面
- 没有草稿恢复容错
- 没有免责声明 gating

## Opinionated Recommendation

如果你现在只是要启动这个项目，前端栈一句话版本就是：

`不要为了将来可能有 H5/App，把今天这个微信小程序做复杂。`

最优方案是：
- 原生微信小程序
- TypeScript
- 自定义组件
- 轻量 request/service 层
- 官方系测试/发布工具

这个选择最符合工程管理上的 4 个原则：
- boring by default
- incremental over revolutionary
- minimal diff
- systems over heroes
